# String investigation

Open **Strings → Grouped string classifier / endpoints / risk indicators** for the entire selected input, or the DEX viewer's **Root views → Strings** groups for exact string-pool values. These are offline observations with physical locations and inspectable rules. Explicit browser search/English translation is available separately; no query is submitted automatically. They do not query VirusTotal or any other service, execute commands, test credentials, connect to endpoints or verify vulnerabilities.

## Groups and evidence

The built-in GPL-3.0-only catalog, version **1.1.0**, has 43 rules and 16 overlapping groups: URLs/URIs, service/API endpoints, DNS-shaped names, IP literals, email candidates, file/registry paths, commands/interpreters, system/execution APIs, credentials/secret candidates, crypto, persistence, anti-analysis/introspection, vulnerability/exploit indicators, dangerous operation/input patterns, encoded data and hashes/identifiers. Root views also expose all candidates, all interesting candidates, unclassified candidates and the complete rule catalog. One string can contribute to several groups; counts are not additive.

Category definitions explain mechanisms and limitations; their labels/rationale participate in catalog identity and are retained once per row. Every match retains a stable rule ID, expression, local validator identity, catalog version/SHA-256, original UTF-16 start/end, physical byte offset/length, observed pattern, implications and a next investigative step. A matched-text preview is explicitly bounded at 512 units; the full original value and exact span remain available. Raw text, encoding, source range, code-point/unit counts, fragmentation and source SHA-256 accompany each record. There is no numeric security score. Secret candidates remain private and are exported only through the user's local document action.

Examples: `CreateRemoteThread` is an API-name observation, not observed injection; `strcpy` requires bounds/input/caller analysis; a CVE ID can occur in a patch note or test; HTTP may be unused or upgraded; an AWS-shaped access key ID is not the secret key itself. DNS-shaped names may be filenames or Java/package identifiers because no TLD/public-suffix/reputation database is consulted. A Base64 candidate is locally decoded only for syntactic round-trip validation, never executed or recursively interpreted. IPv4/IPv6 validation uses local syntax checks with no DNS resolution. Custom untrusted regular expressions are not accepted by this implementation.

## Whole-input decoding

`InputSnapshot` acquires a bounded private byte copy and hashes those exact bytes. `StringDocument` scans the entire copy in five passes: strict UTF-8 (including ASCII), UTF-16LE at each byte alignment, and UTF-16BE at each alignment. All five measured SHA-256 values must agree with acquisition. This is whole-input candidate scanning for these encodings; it does not unpack, decompress, decrypt or recover dynamically constructed strings.

UTF-8 rejects overlong, surrogate and out-of-range encodings. UTF-16 handles surrogate pairs. A UTF-16 run/fragment requires an ASCII graphic anchor, a preceding BOM, or an already admitted preceding fragment. Unicode-only UTF-16 without those anchors can be absent; this is disclosed in metadata. Tabs and code points at/above U+0020 are candidates except C0/C1/DEL, surrogates, Unicode noncharacters, BOM and line/paragraph separators. Being decodable is not evidence that the bytes form a format-defined text field. Several encodings/alignments can overlap. The scanner may include decodable neighboring bytes in a run; match spans separately locate the observed token.

The configured minimum length counts Unicode code points. Long runs split at **8,192 UTF-16 units**, without splitting a surrogate pair; admitted short tails are retained. `runStartPhysicalOffset`, `fragmentIndex` and `runContinues` explain the relationship. Rules operate per fragment, so a pattern spanning a split can be missed. Direction/format controls stay exact in structured data and are displayed as escapes in the viewer. Text values are retained in a private spool; raw byte actions use the same owned byte copy, not an expired original.

Budgets: 256 MiB input, 200,000 admitted fragments, 16 Mi decoded UTF-16 units, one Mi units per classifier call and 2,048 matches per value. Exceeding a budget fails explicitly instead of returning a successful partial index. Private input/text spools are discarded on close/failure/cancellation; process-death cache reclamation and hard process/CPU isolation remain pending. Regex work and upstream parsers are still in process; cancellation is cooperative.

## DEX semantics

`DexStringIndex` classifies every exact decoded value in the selected entry, including embedded NULs and isolated UTF-16 surrogates. It retains original pool IDs and all groups/counts, with a 200,000-interesting-record cap. Its physical token mapping counts **modified UTF-8**: NUL occupies two bytes, and surrogate units each occupy three. The string-data range includes the length prefix/terminator, while `physicalTextOffset` and `textByteLength` locate encoded text only. A pool value does not prove use. Actions link to its pool record and the separate explicit bytecode-reference scan; reflection, other entries/splits and runtime use are outside that scan's scope.

## Navigation, exports and verification

The shared viewer provides 50/10/1-row pages, explicit Search, raw fields/context, group links, exact byte extraction, range measurements and hex. A group export includes **every record in that group**, independently of the UI filter/page, with the common `org.diemobile.evidence-table` schema. It is not an all-groups export unless the all-candidates scope was selected. JSON and range bytes are staged before the document picker; pending stages survive recreation and input expiry. Hex handoff receives a separately owned private copy with SHA-256, so the parent viewer can close without invalidating its bytes. The receiving native viewer retains that copy across recreation and deletes it when finished; abandoned process-death cache files still need reclamation.

Run `bash scripts/test-strings.sh` and `bash scripts/test-dex.sh` with JDK 17. `JSON_JAR` / `DEX_DEPS_DIR` support checksum-verified cached dependencies. Host fixtures check every catalog rule, rejected/accepted IP syntax, UTF-8 across an I/O boundary, odd-aligned UTF-16 and surrogate pairs, BOM-only Unicode, malformed-byte recovery, exact match/range bytes, five-pass identities, fragmentation, complete exports, private byte/text immutability, budgets and cancellation cleanup. DEX fixtures specifically check MUTF-8 byte mapping after NUL, non-ASCII, supplementary and isolated-surrogate values, and retained encoded callers.

`scripts/test-workbench-ui.sh` includes six string viewer cases and one added DEX classification case: grouping/catalog/context, paging/search/Back/recreation, exact UTF-16 extraction, complete filtered-group export after source expiry, cancellation/spool cleanup, independent hex ownership across parent destruction/child recreation, and DEX string-to-caller navigation. These join the previous 24 checks for **31 API 28 Robolectric checks**. They use real engines and byte streams; handset, real SAF providers, API 26/35 lifecycle, performance on large inputs and screen-reader flows remain unverified.

## Readable details and text actions (pre-alpha.17)

Rows summarize why the opened category matched. Structured details prioritize its occurrences, highlight exact matched text, explain the category and preserve source fields/raw JSON. Eight-occurrence pages retain every match and original index. Whole-string and exact-match Copy, search-engine choices and English-translation links require explicit action. Shared selection actions operate on the clearly labelled display text. See [presentation, privacy, limits and test contracts](text-investigation-ui.md). These additions have standalone string/DEX and focused host UI coverage; final full-suite/source/actual Android gates are recorded in the parity checklist.
